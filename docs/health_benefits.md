# 健康权益 / Health Benefits — 产品理念与阶段边界

> 状态：**结构预留，未开放**（`FeatureFlags.healthBenefitsEnabled = false`）
> 本文是「未来做什么、现在不做什么」的约束文档。任何改动「推荐 / 权益 / 商业化」
> 相关代码前，先读第 4 节的隐私红线。

---

## 1. 定位

App 的核心定位不变：**健康报告驱动的长期健康档案管理工具**。

核心链路（P0，始终优先）：

```
报告上传 → OCR 识别 → 指标整理 → 趋势变化 → 器官雷达 → 长期健康档案
```

「健康权益」是**未来的辅助商业化模块**，不是核心功能。上架前不开放，避免商业
内容干扰用户对产品的第一印象。

---

## 2. 命名规范

对用户统一叫 **「健康权益」**。

禁止使用：广告 / 广告中心 / 商城 / 健康商城 / 推荐商品。

用户感知应是「App 为我提供健康相关福利和服务权益」，而不是「App 在向我卖广告」。

---

## 3. 未来承载内容（仅记录方向，现在不实现）

洗牙优惠券 · 口腔检查优惠 · 体检套餐优惠 · 眼科检查 · 骨密度检查 ·
健康筛查服务 · 其他正规健康服务权益 · 品牌合作健康福利。

未来商业模式：用户订阅收入 + 健康服务佣金 + 商家合作费 + 品牌合作费。

---

## 4. 隐私红线（硬约束，不可协商）

**禁止用用户的私人健康数据做商业广告 / 权益定向。**

具体禁止（示例）：

- 检测到血糖高 → 推送糖尿病相关产品
- 报告显示牙齿问题 → 推送某牙科诊所
- 肝功能异常 → 推荐某商业体检机构

以下数据**不得**接入任何商业推荐 / 广告系统：
OCR 报告、检验指标、疾病信息、器官风险、健康趋势。

未来允许的、低敏感的信号只有用户**主动**行为：

- 主动浏览：用户进入「健康权益 → 口腔健康」，可展示洗牙 / 口腔检查 / 牙科优惠
- 主动搜索：用户搜「洗牙」，可展示相关权益
- 城市 / 区域服务：用户主动授予位置权限后，展示当地可用服务

原则：**健康报告数据** 与 **商业系统** 之间不建立直接连接。

---

## 5. 首页展示原则

即使未来正式上线，健康权益也不得占据首页核心位置。首页优先级恒定：

```
1. 健康状态
2. 健康档案
3. 指标变化
4. 器官雷达
5. 健康提醒
6. 健康权益   ← 辅助商业功能，排最后
```

---

## 6. 未来产品流程（草图，现在不实现）

```
健康权益 → 选择分类 → 查看健康服务 → 查看权益详情
        → 免费领取 / 优惠购买 → 生成权益券 → 到店核销
```

例：`健康权益 → 口腔健康 → XX 口腔洁牙 → 原价 ¥300 / App 用户 ¥99 → 领取 → 到店核销`

---

## 7. 数据模型（**现在不建**）

有真实商家和真实核销流程之前不落地任何表 / model，避免投机性设计过早腐烂
（schema 已到 v14，宁可将来带着真实需求重新设计）。

将来大致会有：`HealthBenefit` / `Merchant` / `BenefitCategory` / `Coupon` /
`Redemption`；分类大致为 `dental / physical_exam / eye / bone / vaccine /
screening / other`。仅作方向记录。

---

## 8. 开发优先级

| 级别 | 内容 |
| --- | --- |
| **P0** | 核心链路：报告上传 / OCR / 指标 / 趋势 / 器官雷达 / 长期健康档案 |
| **P1** | 空数据状态、首次使用流程、无报告用户引导、上传体验 |
| **P2** | 轻量预留：`FeatureFlags.healthBenefitsEnabled` + 本文档（**已完成**） |
| **P3** | 暂不开发：商家系统 / 优惠券 / 支付 / 核销 / 广告推荐 / 品牌合作 / 商业后台 |
