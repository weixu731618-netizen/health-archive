# 健康档案 App 开发指令 V0.4D
## DeepSeek 结构化 + 标准指标匹配

当前项目已经完成或正在完成以下能力：

- Flutter 健康档案 App 基础框架
- Drift 本地数据库
- 手工录入健康指标
- 日常健康记录
- 历史记录
- 编辑与删除
- 报告图片上传
- 报告拍摄入口
- 原始报告图片保存
- Mock 报告识别
- 报告确认页
- FastAPI 后端
- 百度 OCR 应用
- 百度 OCR「通用文字识别（高精度含位置版）」接入
- Flutter → FastAPI → 百度 OCR 的真实 OCR 链路

现在进入 **V0.4D：OCR → DeepSeek 结构化 → 标准指标匹配**。

---

# 一、这一版本的核心目标

把百度 OCR 返回的真实文字结果，交给 DeepSeek 做结构化整理。

最终形成：

```text
医院报告图片
→ 百度 OCR
→ OCR 原始文字 / 位置信息
→ DeepSeek 结构化
→ 标准指标匹配
→ 用户确认
→ Drift 入库
```

这一版本成功的标准不是“AI 会看病”。

成功标准是：

> 一张真实医院化验单，可以较准确地转成统一、可保存、可长期跟踪的健康指标。

---

# 二、本版本严格限定范围

本版本只处理 **数值型化验/检验报告**。

优先支持：

- 血常规
- 肝功能
- 肾功能
- 血脂
- 血糖
- 尿常规
- 电解质
- 甲状腺功能
- 凝血
- 肿瘤标志物
- 激素
- 免疫类化验指标

暂时不要处理：

- PDF
- CT
- MRI
- 超声结论
- 胃镜
- 肠镜
- 病理报告
- 心电图图像
- 医生病历
- 处方
- 疾病诊断
- 用药建议
- 风险预测

---

# 三、AI 的职责边界

DeepSeek 只负责：

1. 理解 OCR 文字
2. 判断哪些文字属于同一个检查项目
3. 提取结构化字段
4. 将原始指标名称映射到内部标准指标
5. 返回严格 JSON

DeepSeek 不负责：

- 判断用户患有什么疾病
- 给出治疗建议
- 给出药物建议
- 自动补齐报告里不存在的参考范围
- 自动补齐报告里不存在的单位
- 自动猜测看不清的数值
- 自动诊断

原则：

> 报告里没有的信息，一律返回 null，不允许凭医学常识补全。

保持现有 Flutter 与 FastAPI 解耦。

推荐结构：

```text

  ↓
```

Flutter 页面不能直接调用：

- 百度 OCR

# 七、DeepSeek 输入内容

不要直接把整张图片再发送给 DeepSeek。

本版本输入 DeepSeek 的内容是：

1. 百度 OCR 识别出的文字
2. OCR 返回的位置信息
3. 必要的行序 / 坐标关系

例如概念输入：

```json
{
  "lines": [
    {
      "text": "尿酸",
      "left": 120,
      "top": 500,
      "width": 80,
      "height": 28
    },
    {
      "text": "480",
      "left": 420,
      "top": 500,
      "width": 65,
      "height": 28
    },
    {
      "text": "μmol/L",
      "left": 560,
      "top": 500,
      "width": 100,
      "height": 28
    },
    {
      "text": "210-420",
      "left": 760,
      "top": 500,
      "width": 100,
      "height": 28
    }
  ]
}
```

---

# 八、DeepSeek 输出必须是严格 JSON

禁止返回：

- Markdown
- 解释文字
- 医疗建议
- “根据您的报告……”
- 代码块以外的自然语言

统一返回：

```json
{
  "hospitalName": "深圳XX医院",
  "reportDate": "2026-08-18",
  "reportType": "生化检查",
  "patientName": "张某某",
  "metrics": []
}
```

# 九、StructuredMedicalReport 数据结构

至少包含：

```text
hospitalName
reportDate
reportType
patientName
metrics
```

如果某字段无法从报告中确定：

返回 null。

不要猜测。

# 十、RecognizedMetric 数据结构

每个指标至少包含：

```text
rawName
canonicalName
matchedMetricId
value
unit
referenceMin
referenceMax
referenceText
originalStatus
bodySystem
confidence
```

例如：

```json
{
  "rawName": "血清肌酐",
  "canonicalName": "肌酐",
  "matchedMetricId": "CREA",
  "value": 93,
  "unit": "μmol/L",
  "referenceMin": 57,
  "referenceMax": 111,
  "referenceText": "57-111",
  "originalStatus": null,
  "bodySystem": "肾脏",
  "confidence": 0.97
}
```

---

# 十一、数值字段必须是数值

如果报告结果是：

```text
480
```

value 返回：

```json
480
```

不要返回：

```json
"480 μmol/L"
```

单位必须单独放在 unit。

---

# 十二、特殊结果处理

有些报告不是纯数字，例如：

- 阴性
- 阳性
- 弱阳性
- 未检出
- +
- ++
- <0.01
- >1000

不要强行转成数字。

数据模型需要允许：

```text
numericValue
textValue
qualifier
```

例如：

```json
{
  "numericValue": 0.01,
  "qualifier": "<",
  "textValue": null
}
```

或者：

```json
{
  "numericValue": null,
  "qualifier": null,
  "textValue": "阴性"
}
```

不要因为无法转换成 double 就丢掉数据。

---

# 十三、参考范围处理

支持：

```text
3.9-6.1
3.9 ～ 6.1
< 6.1
≤ 6.1
> 40
阴性
```

需要保留原始：

```text
referenceText
```

只有能够明确解析时才写：

```text
referenceMin
referenceMax
```

不能解析：

```text
referenceMin = null
referenceMax = null
```

---

# 十四、状态判断原则

最终：

- 正常
- 偏高
- 偏低
- 未判断

优先由后端或 Flutter 本地规则计算。

不要完全相信 AI 返回的状态。

如果有：

```text
value
referenceMin
referenceMax
```

则程序计算：

```text
value > referenceMax → 偏高
value < referenceMin → 偏低
其他 → 正常
```

如果参考范围无法计算：

```text
未判断
```

原报告里的：

- H
- L
- ↑
- ↓
- *
- 异常

可以保存为 `originalStatus`，但不能取代数值规则。

# 十五、建立标准指标字典

这一版的核心之一是：

**同一个医学指标，无论医院叫什么名字，都尽量归到同一个 metricId。**

不要让数据库出现：

```text
肌酐
血清肌酐
Cr
CREA
Creatinine
```

五个不同历史曲线。

它们应该统一映射到：

```text
metricId = CREA
canonicalName = 肌酐
```

# 二十一、不要一次手工写死所有医学指标

首版先建立：

50～100 个最常见指标。

架构必须允许以后不断扩展：

```text
metric_dictionary
```

而不是每加一个指标就改多个页面代码。

---

# 二十二、指标匹配流程

建议匹配顺序：

```text
1. 标准 metricId 精确匹配
2. canonicalName 精确匹配
3. alias 忽略大小写匹配
4. 去空格、横杠、括号后的标准化匹配
5. DeepSeek 建议匹配
6. 无法确认 → unmatched
```

不要因为大模型觉得“像”就强制匹配。

---

# 二十三、匹配置信度

可以定义：

```text
exact
alias
ai_suggested
unmatched
```

或者数值 confidence。

AI 建议匹配的项目在确认页显示：

```text
建议匹配
```

让用户重点检查。

---

# 二十四、无法匹配指标必须保留

例如 OCR 识别：

```text
载脂蛋白B
```

但字典还没建立。

不要删除。

保存：

```text
rawName = 载脂蛋白B
matchedMetricId = null
canonicalName = null
```

确认页显示：

```text
未匹配标准指标
```

允许用户：

- 直接以未分类指标保存
- 手动选择标准指标

---

# 二十五、单位标准化

需要建立基础单位标准化。

例如：

```text
umol/L
μmol/L
µmol/L
```

统一展示为：

```text
μmol/L
```

例如：

```text
10^9/L
10⁹/L
×10^9/L
```

可以统一展示格式。

但是：

不要自动进行医学单位换算，除非换算规则明确且经过单独测试。

V0.4D 首版只做：

**单位名称标准化，不做数值换算。**

# 三十一、DeepSeek Prompt 设计

后端需要建立专门的系统 Prompt。

核心要求：

```text
你是医疗检验报告结构化工具，不是医生。

你的任务仅是根据 OCR 内容提取报告中明确存在的信息。

禁止使用医学知识补全报告没有的信息。

看不清或无法确定的字段必须返回 null。

必须严格按照 JSON Schema 输出。

不要诊断疾病。
不要给治疗建议。
不要给用药建议。
不要解释检查结果。
```

Prompt 与业务代码分离，方便以后修改。

---

# 三十二、JSON Schema 校验

后端收到 DeepSeek 返回后：

必须使用 Pydantic / JSON Schema 校验。

流程：

```text
DeepSeek 返回
↓
JSON parse
↓
Schema validate
↓
通过 → 返回 Flutter
失败 → 重试一次或返回识别失败
```

禁止把格式错误的模型输出直接交给 Flutter。

---

# 三十三、模型失败策略

DeepSeek 出现：

- 超时
- 返回非 JSON
- JSON Schema 不匹配
- 空结果
- 服务不可用

提示：

```text
报告结构化失败，请重新识别或使用手工录入。
```

不要删除原始图片。

不要写入数据库。

---

识别流程建议状态：


方便以后恢复任务。

# 三十八、本版本验收场景

例如上传一张真实报告：

```text
血清肌酐 93 μmol/L 57-111
尿酸 480 μmol/L 210-420
ALT 32 U/L 9-50
HbA1c 6.8 % 4.0-6.0
```

系统应该形成：

```text
CREA → 肌酐 → 93
UA → 尿酸 → 480
ALT → 丙氨酸氨基转移酶 → 32
HBA1C → 糖化血红蛋白 → 6.8
```

然后进入确认页面。

用户确认后才进入 Drift。

# 四十、本版本不要开发趋势分析

# 四十四、本版本最终成功标准

V0.4D 成功必须满足：

1. 上传真实化验单
2. 百度 OCR 真实识别
3. DeepSeek 返回严格结构化 JSON
4. 同一指标不同写法可以映射到统一 metricId
5. 不确定的数据不会被模型猜测补全
6. 未匹配指标不会丢失
7. 用户可以对照原图确认
8. 只有用户确认的数据才进入 Drift
9. 同一标准指标以后能够形成统一历史曲线
10. App 不提供疾病诊断和治疗建议

核心原则：

> **先把健康数据做准确、做统一，再谈分析。**

# 五十二、MVP 产品成功定义

MVP 成功不是页面数量多，也不是 AI 功能多。

MVP 成功定义：

> 一个成年人可以把真实医院化验单拍照或上传，系统自动读取和整理检查指标，用户核对后保存；未来再次检查时，能够持续积累同一指标的历史数据，并随时回看原始报告，同时数据可以被导出或彻底删除。

在达到这个标准之前：

**优先修稳定性，不继续扩大功能范围。**

达到这个标准之后，再进入：

```text
V0.4E：扩充数值型报告覆盖
```

以及后续：

```text
V0.5：文字结论型报告（超声 / CT / MRI 等）
V0.6：趋势分析
V0.7：疾病史 / 用药时间线关联
V0.8：手机号登录 / 云同步 / 备份
```
